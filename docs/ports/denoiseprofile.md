# Port spec: denoise (profiled) (denoiseprofile)

Source: darktable (the reference release, commit 20891f6c6f), `src/iop/denoiseprofile.c` (`legacy_params_to11()`, `legacy_params()`, `reload_defaults()`, `commit_params()`, `process()`, `process_wavelets()`, `process_nlmeans()`, `process_variance()` and their helpers: `compute_wb_factors()`, `set_up_conversion_matrices()`, `invert_matrix()`, `precondition_v2()`, `precondition_Y0U0V0()`, `backtransform_v2()`, `backtransform_Y0U0V0()`, `variance_stabilizing_xform()`, `nlmeans_norm()`, `nlmeans_scattering()`, `nlmeans_precondition()`, `nlmeans_backtransform()`, the `infer_*_from_profile()` and `dt_iop_denoiseprofile_get_auto_profile()`), with helpers from `src/common/eaw.c` (`eaw_dn_decompose()`, `dn_weight()`, `eaw_synthesize()`, `accumulate()`), `src/common/nlmeans_core.c` (`nlmeans_denoise()`, `define_patches()`, `scatter()`, `init_column_sums()`), `src/common/noiseprofiles.c` (`dt_noiseprofile_get_matching()`, `dt_noiseprofile_interpolate()`, `dt_noiseprofile_generic`), `src/common/math.h` (`dt_fast_mexp2f()`, `fast_mexp2f()`, `dt_log2f()`), `src/gui/draw.h` and `src/common/curve_tools.c` (`dt_draw_curve_calc_values()`, `CurveDataSample()`, Catmull-Rom), and the data file `data/noiseprofiles.json`. The OpenCL path is `process_cl()` with `data/kernels/denoiseprofile.cl`. The reference is darktable's CPU path.

Status: **specified, not yet ported.** darktable's module is large (3,798 lines of C, two denoising algorithms, two colour modes and a third, diagnostic mode), so the port is split into slices, build tasks in order (Slices). Built so far: the camera's identity in the image context (slice 1) and the export's tiles sized beside held whole-image scratch (slice 5). The design rests on architecture decisions 13, 15, 24 and 32.

Golden cases planned (darktable tests on `mire1.cr2`, a Canon EOS 40D at ISO 1600, 3908×2602, colorin made an identity so both renders are camera RGB): 0013-denoiseprofile-wavelets (wavelets, Y0U0V0, params version 10), 0143-denoiseprofiled-wave-rgb (wavelets, RGB, version 11) and 0027-denoiseprofile-nlmeans (non-local means, version 10). All three autodetect the profile, which for this raw is an exact ISO match.

## Purpose

Denoise (profiled) removes sensor noise using a model of the camera's noise measured at each ISO: noise of variance a·x + b at signal x, Poissonian (photon) noise plus Gaussian (read) noise. A variance-stabilising transform (a generalised Anscombe transform, darktable's "v2" with an extra exponent, the shadows setting) makes the noise level the same everywhere, so one threshold fits the whole image; then either an edge-aware à-trous wavelet decomposition is soft-thresholded scale by scale, each threshold from the band's measured variance (BayesShrink), or each pixel becomes a weighted mean of pixels whose surrounding patches look alike (non-local means). The inverse transform, with a bias correction, brings the image back. The wavelets can work on RGB or on Y0U0V0, a luminance and two colour-difference channels weighted by the white balance, so luma and chroma noise are treated apart, which is darktable's default.

In Apertrust it is the operation behind the first pass's Denoise (profiled) module, in the Correct tab (decisions 2 and 38; `docs/modules/README.md`, Denoise (profiled)).

## Pipeline

- **darktable position:** 9.0 in the v5.0 order (`src/common/iop_order.c`, `v50_order`), the first operation after demosaic (8.0), before bilateral (10.0), lens correction (13.0) and haze removal (14.0). The tests' sidecars use the v3.0 order (`iop_order_version` 2), which has it at the same place.
- **Apertrust slot:** camera RGB 9, darktable's (decision 22), between demosaic (raw 8) and haze removal (camera RGB 14). A row in `docs/engine.md`'s Order table: `denoiseprofile | camera RGB 9 | no | 9.0, first after demosaic | Denoise (profiled)`.
- **Domain:** scene-referred, linear in and out.
- **Input and output:** RGBA, `default_colorspace()` `IOP_CS_RGB`: camera RGB, demosaiced and white balanced by temperature; output in the same space.
- **Assumes earlier modules:** demosaic; temperature, whose coefficients (`piece->pipe->dsc.temperature.coeffs`, Apertrust's `ImageDesc::white_balance`) set the transform's per-channel noise scale and the Y0U0V0 matrix; the noise model is the raw's, so nothing between the sensor and this module may change levels (rawprepare's normalisation is assumed, exposure comes later). The profile needs the camera's make, model and ISO (The noise profiles).
- **Layer support:** yes (`docs/modules/README.md`). darktable's wavelet thresholds come from the instance's own input, so an instance on a layer measures its own input.
- **darktable's tiling:** `tiling_callback()`: overlap `P + K_scattered` for non-local means (below); for wavelets `1 << max_scale`, 128 at full resolution, with each tile measuring its own band variances. darktable-cli's export of the tests' 10 MP image with `resourcelevel=reference` (8 GB) does not tile: the wavelets' working set, factor 5 of 16 bytes a pixel, is 0.8 GB.

**Defaults from the image** (`reload_defaults()`, Apertrust's `Operation::defaults(image)`): darktable looks the profile up for the image (`compensate_hilite_pres` from the photo's shift), stores its `a` and `b` with `a[0] = −1` when it was found or interpolated, and sets `radius = infer_radius(a[1])`, `scattering = infer_scattering(a[1])`, `shadows = infer_shadows(a[1])`, `bias = infer_bias(a[1])`. For mire1 at ISO 1600, `a[1] = 3.2148e-5`: radius 1, scattering 0.0964, shadows 1.1345, bias −0, the values all three tests store.

**The schema** (version 1, Apertrust's count): every field above under darktable's name, the curves as `y_<channel>_<band>` (`all`, `r`, `g`, `b`, `y0`, `u0v0`; bands 0 to 6), `x` left out (fixed), the two compatibility flags left out (fixed on), and the profile as `profile_auto` (bool, default true) with `profile_a` and `profile_b` (green's, the only values processing reads), used while `profile_auto` is off (decision 24: on the reference release's file no two profiles of a camera share green's values while differing elsewhere, so they identify the chosen profile as darktable's six do). `profile_a` is above 0 (1e-12 at least); `profile_b` may be negative (806 of the 8,151 profiles, down to −6.05e-4). Defaults as `reload_defaults`: `profile_auto` on when the lookup found or interpolated a profile, off on the generic one, and `profile_a` and `profile_b` the lookup's green values either way, so turning Auto off keeps the render. The introspection's ranges become hard limits, the soft ranges the module's.

## The noise profiles

**The data.** `data/noiseprofiles.json` at the reference release: 1.8 MB, version 0, 436 models under their makers, 8,641 profiles, each `{name, iso, a[3], b[3]}` and optionally `skip`. It is darktable's, GPL like the rest of darktable, so Apertrust can ship it under its own GPL-3.0-or-later with its provenance.

**How Apertrust ships it** (decisions 24 and 45): the file verbatim at `data/noiseprofiles.json`, the repository's top-level data folder, darktable's own path (1,813,484 bytes at the reference release, git blob ef75add7a2, SHA-256 d206530db4921482cd73aa4ad9bb53561b33f50d6499664298bb14520734afb3, its entry in `data/README.md` and a test in the denoise crate holding the checksum), embedded by the denoise crate alone with `include_str!` and parsed once, on first use, into a map from (maker, model) to profiles sorted by ISO, behind a `OnceLock`. Verbatim keeps a later release's file a copy, its diff reviewable against darktable's. Parsing uses `serde_json` (MIT OR Apache-2.0, pure Rust; it brings `itoa` and `ryu`, while `memchr` and `serde_core` are already in the lock), a dependency within the rules: `cargo deny check` runs when it is added, and `tools/credits.sh` regenerates `CREDITS.md`. The file is not converted to TOML or Rust: that would need a converter, which needs a JSON parser of its own, and trust that its numbers are darktable's.

**Lookup, as darktable does** (`dt_noiseprofile_get_matching`, `dt_iop_denoiseprofile_get_auto_profile`):

1. The first maker entry whose `maker` is a substring of the image's maker, then the model whose `model` equals the image's model exactly; its profiles without `skip: true`, as doubles converted to f32, sorted by ISO (`g_list_sort`, stable, after the list was built by prepending, so of two profiles with one ISO the later in the file comes first).
2. The ISO: `int iso = exif_iso` (truncated), shifted right by the highlight preservation shift when `compensate_hilite_pres` is on (`iso >>= shift`, `shift = max(⌊exif_highlight_preservation⌋, 0)`).
3. Walking the sorted profiles: one with exactly that ISO is the profile; otherwise, between the last profile below and the first above, `t = clamp((iso − iso₁) / (iso₂ − iso₁), 0, 1)` in f32 and `a = (1 − t) a₁ + t a₂`, `b` likewise (`dt_noiseprofile_interpolate`).
4. No camera, no model, or an ISO below the lowest or above the highest profile: darktable's generic Poissonian profile, `a = 1e-4`, `b = 0` for every channel, and the auto flag stays unset.

**Names.** darktable matches its own canonical names, rawspeed's camera IDs (`canonical_make`, `canonical_model` from `cameras.xml`), never an alias. Apertrust's decoder gives rawler's `clean_make` and `clean_model`, where an alias (the EOS Digital Rebel XTi for the EOS 400D) has the alias's own clean name. Measured on darktable's file against rawler 0.8.0's camera files:

- 384 of the 436 profiled models equal a rawler camera's clean make and model;
- 69 rawler aliases lead to a profiled canonical model, which only a map from rawler's alias to its camera's `clean_model` reaches;
- 8 profiled models equal only an alias's clean name in rawler (the Nikon D800E, seven Panasonics), and darktable's canonical name may be the other;
- 44 profiled names match no rawler name: some naming differs (darktable's `Z 6_2`, `Z 7_2`, `Z6_3`, `Z50_2`, `Z5_2` against rawler's `Z 6 2` and `Z 5 II`; maker `OM System` against rawler's `OM Digital Solutions`), the rest rawler does not know by that name (phones and other DNGs, Ricoh GR, Pentax K-01 to K-500, several GFX).

On the raw.pixls.us corpus (40 samples; darktable's names from rawspeed's `cameras.xml` at darktable's submodule commit c835b05a, EXIF ISO by exiftool), rawler's names give the same profile as darktable's on 34; of the other six, five are files neither knows (phone DNGs, a GoPro GPR, a Hasselblad 3FR, a Sigma X3F; generic on both), and one, the OM-1 Mark II, finds its ISO 200 profile in darktable and the generic one with rawler's maker.

**The names Apertrust uses** (decisions 24 and 27): the image context's camera carries darktable's `camera_model` as `model`, the main camera's clean name with an alias resolved, and darktable's `camera_alias` as `alias`, the name the file's camera has. `apertrust-raw` resolves aliases from rawler's own data: rawler embeds its camera files as `rawler::decoders::CAMERAS_TOML` and parses them with `toml` 0.8.23, already a workspace dependency, so `apertrust-raw` parses them once, lazily, to map each alias to its camera's main clean model, keyed as rawler matched the file; no generated table, nothing to regenerate when rawler updates. darktable's spellings that differ from rawler's (Nikon's `Z 6_2`, `Z 7_2`, `Z6_3`, `Z50_2`, `Z5_2`; maker `OM System`; Fujifilm's `GFX100S` and `GFX100 II`) are a hand-written list in `apertrust-raw`, applied to `make`, `model` and `alias` there, so the image context's names are darktable's. The lookup tries the alias (the D800E and the Panasonics darktable profiles under their own names), then the model (the 69 aliases and the renamed cameras), the maker by darktable's substring rule. Tests: every rename's target is a profiled model; every profiled darktable model a rawler camera reaches resolves; on the corpus, where present, all 40 agree with darktable's choice.

The alias resolution is checked against rawspeed's `cameras.xml` at c835b05a: of rawler's 120 aliases, 119 have rawspeed's alias name (Minolta's `ALPHA 7D` is rawspeed's `Alpha 7D`) and 89 resolve to rawspeed's main model; the other 31 are cameras the two group differently (the D800E, the FinePix S6000fd, the Phase One P25+, the Dynax 7D and 27 Panasonics: rawspeed's G8 is rawler's G80, its FZ82 rawler's FZ80, its own DC-G95, DMC-GX85 and DMC-FZ2000 are rawler's aliases), which the lookup's alias first reaches; none of the corpus's 40 samples is an alias. If rawler kept an alias's main name itself, the parse of its camera files could go.

**ISO** (decision 24). darktable reads `exif_iso` (`src/common/exif.cc`) through Exiv2's `isoSpeed`, which tries the standard and maker-note ISO tags in order, takes the second value of a two-value ISOSpeedRatings (Nikon's Lo and Hi modes), and at 65535 or with no tag takes the tag Exif.Photo.SensitivityType names; then, at 0 or 65535, darktable takes Pentax's maker-note ISO or, for the EXIF makers `SONY` and `Canon` only, RecommendedExposureIndex. rawler has ISOSpeedRatings (its first value), ISOSpeed, RecommendedExposureIndex and SensitivityType, and no maker notes. Apertrust's `iso`, in `apertrust-raw`, follows darktable's rule as far as those reach: ISOSpeedRatings when its first value is above 0, its second value where the file holds two, which rawler's IFDs show only in a DNG, otherwise its first; at 65535 or missing, the tag SensitivityType names, in Exiv2 0.28's `isoSpeed` order (`easyaccess.cpp`, the same in 0.28.3 and 0.28.5): the first present of the tags its value names, whatever their value, for 1 StandardOutputSensitivity, 2 RecommendedExposureIndex, 3 ISOSpeed, 4 RecommendedExposureIndex or StandardOutputSensitivity, 5 ISOSpeed or StandardOutputSensitivity, 6 ISOSpeed or RecommendedExposureIndex, 7 all three in that order, StandardOutputSensitivity never found, since rawler does not read it, so the rating stays; then, at 0 or 65535, RecommendedExposureIndex for the makers `SONY` and `Canon`, as the file's EXIF spells them; 0 when none. Maker-note ISOs and StandardOutputSensitivity stay recorded differences until the metadata reader (decision 5's exiftool-rs) reads them.

**Highlight preservation** (`_check_highlight_preservation` in `src/common/exif.cc`): darktable estimates it from maker notes, Canon's Auto Lighting Optimizer, Fujifilm's DR100/200/400, Nikon's Active D-Lighting and HLG, Olympus's gradation, Pentax's dynamic range expansion; only a whole EV counts (Fujifilm DR200 and DR400, Nikon HLG and Active D-Lighting extra high, Pentax's expansion). rawler reads no maker notes, so the shift is 0 and the toggle's default off until the decoder supplies it (Deliberate differences, 6).

**Where it runs.** The profile is the operation's data, so the database and the lookup live in its crate, and `prepare` and `defaults` look the profile up from the image context, whose `Camera` carries `make`, `model`, `alias` and `iso` (decision 24), filled by the engine's `raw::image_context` from `apertrust-raw`. A crate function, `profiles(camera)`, lets the module list a camera's profiles later; how the list reaches the module, which depends on no operation crate, is the module builder's design.

## Setup on the CPU (`commit_params`, `process_*` set-up)

From the parameters and the image, in `crates/op/denoiseprofile/src/setup.rs`, `prepare`:

- **Profile.** `profile_auto` (darktable's `a[0] == −1`): the lookup above; else `profile_a`, `profile_b`. Processing reads `a = a[1]`, `b = b[1]` only.
- **Auto modes.** In non-local means auto and wavelets auto, with `g = a × overshooting`: `radius = min((unsigned)(1 + 15000 g + 300000 g²), 8)`, `scattering = min(3000 g, 1)`, `shadows = min(max(0.1 − 0.1 ln g, 0.7), 1.8)`, `bias = −max(5 + 0.5 ln g, 0)` (the `0.1` and `0.5` are doubles in darktable, so these run in f64 and are stored as f32); otherwise the parameters as set.
- **Wavelet forces** (`dt_draw_curve_calc_values` over a Catmull-Rom curve through the seven `(x, y)` of each channel, sampled at the seven `k/6`, `CurveDataSample`): `force[ch][k] = ⌊clamp(curve(k/6), 0, 1) × 65535 + 0.5⌋ / 65536`. With `x` fixed at `k/6`, `curve(k/6) = y[ch][k]`, so `force = ⌊clamp(y, 0, 1) × 65535 + 0.5⌋ / 65536`: 0.5 stays 0.5, 1 becomes 65535/65536. Apertrust evaluates darktable's curve with `apertrust_color::curve`'s Catmull-Rom, so the sampling is darktable's.
- **White balance factors** (`compute_wb_factors`, with `fix_anscombe_and_nlmeans_norm` on): `c` the input's `white_balance`, `m = (c₀ + c₁ + c₂)/3`; `wb = c` when `wb_adaptive_anscombe` and `m ≠ 0`, `(1, 1, 1)` when `m = 0` (darktable's JPEGs; Apertrust's descriptor is 1 before temperature, so a non-raw gets `wb = (1, 1, 1)` the same way), otherwise `(m, m, m)`.
- **Scale.** Wavelets: `s = min(roi_in->scale / piece->iscale, 1)`; non-local means: `s = min(min(roi_in->scale, 2) / max(iscale, 1), 1)`. Both are the image context's `scale` in Apertrust (at most 1).
- **The transform's exponent and gain:** `p_c = max(shadows + 0.1 ln(s / wb_c), 0)` per channel, with the unscaled `wb` (f64 arithmetic, as darktable's `0.1` is a double); `compensate_p = 0.05 / 0.05^shadows`; `A = a × compensate_p`, `B = b`.

**Wavelets only** (`process_wavelets`):

- **Scales:** `supp0 = min(257, 0.2 × max(W, H))` with W × H the full-resolution input (darktable's `piece->buf_in` times `iscale`), `i0 = log2((supp0 − 1)/2)`; N, `max_scale`, is the first n in 0 to 6 with `1 − (log2(((4·2ⁿ + 1)/s − 1)/2) − 1 + 0.5) / i0 < 0`, else 7 (darktable's `dt_log2f` is `log2f` on glibc and `logf(f)/logf(2)` elsewhere; it is only compared with 0). For mire1 at full resolution N = 7 (dilations 1 to 64); at s = 1/4, N = 5. Band of scale n: `N − 1 − n`, so a scale keeps its physical frequency's curve at every pipe scale.
- **Small images:** W or H below `2^N` at the pipe's scale: the output is the input.
- **Y0U0V0 matrices** (`set_up_conversion_matrices(wb)`, unscaled `wb`): row 0 `√3 (1/wb₀ + 1/wb₁ + 1/wb₂) / wb_c`; row 1 `(0.5, 0, −0.5) / √(0.25 wb₀² + 0.25 wb₂²)`; row 2 `(0.25, −0.5, 0.25) / √(0.0625 wb₀² + 0.25 wb₁² + 0.0625 wb₂²)`; `R` its inverse by cofactors in f32 (`invert_matrix`); if the determinant is 0, row 0 becomes `1/(3 σ_Y0)`, `σ_Y0 = √((wb₀² + wb₁² + wb₂²)/9)`, and is inverted again.
- **Strength:** `cs = 2.5` in Y0U0V0, 1 in RGB; `k = strength × cs × s`; `M' = M / k`, `R' = R × k`, `wb' = wb × k`.
- **Per scale n:** `σₙ = varf^n` with `varf = √(2 + 2·16 + 36)/16 = √70/16 ≈ 0.5229` (`powf` in f32), `σₙ²`, `1/σₙ²`; the force's factor `adjtₙ`: RGB, `8 · 4 force[all][band]² · 4 force[c][band]²` per channel; Y0U0V0, `8 · 4 force[Y0][band]²` for channel 0 and `8 · 4 force[U0V0][band]²` for 1 and 2.
- **Backtransform's bias:** `bias' = bias − 0.5 ln(s)`.

**Non-local means only** (`process_nlmeans`, `nlmeans_denoise`):

- `P = ⌈radius × s⌉`; `K = (int)nbhood`; `scattering` as set in an export at any scale (`nlmeans_scattering` changes K and the scattering only for darktable's fast, preview, thumbnail and canvas pipes; Apertrust keeps the export's rule in every pipe, decision 15).
- `norm = 0.045 / (2P + 1)²` (`nlmeans_norm`); `cpw' = central_pixel_weight × s`; `cp = cpw' × (2P + 1)²` (`compute_center_pixel_norm`).
- `wb' = wb × strength × s` (no 2.5).
- **The offsets** (`define_patches`, `scatter`), computed on the CPU in f64 exactly as darktable's doubles: for row index i and column index j, each from −K to K, row-major, `r = scatter(i, j)`, `c = scatter(j, i)`, `scatter(u, v) = (int)(s × ((|u|³ + 7|u|√|v|) sgn(u) × scattering / 6 + u))`; `(2K + 1)²` offsets, duplicates kept, as a table of int pairs (up to 3,721). Their largest |r| or |c| is the search reach `R`: 14 for test 0027 (K 7, scattering 0.0964).

## Wavelets (`process_wavelets`, `eaw_dn_decompose`, `eaw_synthesize`)

Per pixel, then over the image, in processing order:

1. **Transform** (`precondition_v2` for RGB, `precondition_Y0U0V0`):
   - RGB: `Tc = 2 · max(inc / wb'c + B, 0)^(1 − pc/2) / ((2 − pc) √A)`.
   - Y0U0V0: `tc = max(inc + B, 0)^(1 − pc/2) · 2 / ((2 − pc) √A)`, no division by the white balance, then `T = M' t`.
2. **Decomposition**, n = 0 to N − 1, `c₀ = T` (`eaw_dn_decompose`): `cₙ₊₁(x) = Σ f_i f_j w(x, y) cₙ(y) / Σ f_i f_j w(x, y)` over `y = x + 2ⁿ (i, j)`, i, j from −2 to 2, coordinates clamped to the image (nearest pixel), `f = (1, 4, 6, 4, 1)/16`; one weight for all channels, `w = fast_mexp2f(max(0, 0.02 · |cₙ(x) − cₙ(y)|² / σₙ² − 9))` with the squared distance over the three channels (`dn_weight`). The band is `dₙ = cₙ − cₙ₊₁`, and its sum of squares over every pixel of the image at the pipe's scale, `Sₙ` per channel.
3. **Thresholds** (`variance_stabilizing_xform`): `thrₙ,c = adjtₙ,c · σₙ² / √max(1e-6, Sₙ,c / (npixels − 1) − σₙ²)`.
4. **Synthesis** (`eaw_synthesize`, `accumulate`): `O = Σₙ soft(dₙ, thrₙ) + c_N`, `soft(d, t) = max(d − t, 0) + min(d + t, 0)`; boost 1.
5. **Inverse transform** (`backtransform_v2`, `backtransform_Y0U0V0`):
   - RGB: `x = max(Oc, 0)`; `z = (x + √max(x² + bias', 0)) · √A (2 − pc) / 4`; `outc = wb'c (z^(1/(1 − pc/2)) − B)`.
   - Y0U0V0: `r = R' O`; `x = max(rc, 0)`; `z = (x + √max(x² + bias' · wb'c, 0)) · √A (2 − pc) / 4`; `outc = z^(1/(1 − pc/2)) − B`.

With `bias' = 0` and every threshold 0, steps 1 and 5 are each other's inverse for non-negative input, and the à-trous decomposition reconstructs exactly, so the operation is an identity only in that limit, which `strength → 0` approaches without reaching (Tool binding notes).

**`fast_mexp2f`** (`src/common/math.h`), darktable's deliberately kept low-precision 2^−x: `k0 = 1065353216.0f + x · (−8388608.0f)` in f32 (the product is exact, a power of two; the sum rounds to a multiple of 64), then `bitcast<f32>((int)(k0 ≥ 8388608.0f ? k0 : 0))`. Piecewise linear in x, `1 − x/2` on [0, 1], halving its slope each octave. WGSL's f32 add and multiply are correctly rounded and its float-to-int conversion truncates, so the kernel reproduces it bit for bit.

## Non-local means (`process_nlmeans`, `nlmeans_denoise`)

1. **Transform** (`nlmeans_precondition`, `precondition_v2`): `Tc = 2 · max(inc / wb'c + B, 0)^(1 − pc/2) / ((2 − pc) √A)`, RGB only (non-local means has no Y0U0V0).
2. **Weights:** for each offset q = (r, c) of the table with x + q inside the image (an offset whose partner is outside is skipped, contributing nothing):
   - the patch distortion `D = Σ_{u ∈ [−P, P]²} Σ_ch (T(x + u) − T(x + u + q))²`, counting only the u where both x + u and x + u + q lie inside the image. darktable reaches this with column sums slid down each 72 × 60 chunk (`init_column_sums` and the row updates): a column contributes only while both its pixels are inside, a row only while both its rows are; chunks change the sums' rounding, not their terms;
   - `diss = (D + cp · Σ_ch (T(x) − T(x + q))²) / (1 + cpw')`;
   - `w = dt_fast_mexp2f(max(0, diss · norm − 2))`, the integer variant: `bitcast<f32>(k0 ≥ 0x800000 ? k0 : 0)`, `k0 = 0x3f800000 + (int)(x · (−8388608.0f))`. The offset (0, 0) always weighs 1.
3. **Mean:** `U(x) = Σ_q w T(x + q) / Σ_q w`, over the three channels.
4. **Inverse transform** (`nlmeans_backtransform`, `backtransform_v2`): RGB's, with `wb'` and `bias'`.

## Compute variance (`process_variance`)

A profiling aid: the output is the input, and the variance of the transformed image per channel (`sum_rec`, `variance_rec`) goes to three labels in the module. darktable offers it only behind the preference `plugins/darkroom/denoiseprofile/show_compute_variance_mode`, and its OpenCL path refuses it. Not ported: `prepare` returns `NotPorted` (Deliberate differences, 2).

## GPU plan

Every pass is `[numthreads(16, 16, 1)]`, one invocation per pixel of what it writes. `pow0` throughout, after the `max(…, 0)` darktable takes.

**Wavelets**: scratch `C0`, `C1` (the coarse levels, ping-ponged) and `A` (the accumulated thresholded bands), each an RGBA image of the whole image at the pipe's scale; `Pp`, the per-workgroup partial sums, ⌈W/16⌉·⌈H/16⌉ float4; `S`, the N band sums, one float4 each.

| Pass | Kind | Size | Reads | Writes |
| --- | --- | --- | --- | --- |
| `precondition` | whole-image | the input (a tile's region in an export's first round) | the input pixel | `C0` at the pixel's absolute position; `A = 0` |
| `decompose`, n = 0 to N − 1 | whole-image | the whole image | `cₙ`'s 5×5 taps at dilation 2ⁿ; for n ≥ 1, `cₙ₋₁(x)`, `cₙ(x)` and `Sₙ₋₁` | `cₙ₊₁` over `cₙ₋₁`'s buffer; for n ≥ 1, `A(x) += soft(cₙ₋₁(x) − cₙ(x), thrₙ₋₁)`; the workgroup's partial sum of `dₙ²` into `Pp` |
| `combine`, n = 0 to N − 1 | whole-image | one workgroup | `Pp` | `Sₙ` |
| `main` | per pixel | the output | `A`, `c_N`, `c_{N−1}`, `S_{N−1}`, the input's alpha | the pixel: `O = A + soft(c_{N−1} − c_N, thr_{N−1}) + c_N`, inverted |

Each `decompose` reads `cₙ₋₁` and writes `cₙ₊₁` at its own pixel only, and the taps it reads are in the other buffer, so folding scale n − 1's synthesis into scale n's decomposition is race-free and saves N passes. 2N + 2 passes: 16 for mire1. Uniform blocks: `precondition`'s holds the transform (`p`, `A`, `B`, `wb'`, `M'`, the mode); each `decompose` its dilation, `1/σₙ²`, the previous scale's `σ²` and `adjt`, the pixel count; `main` the inverse (`bias'`, `R'`, `wb'`, `p`, `A`, `B`) and the last scale's `σ²` and `adjt`. Only `main` reads the bias, so a bias drag reruns one pass once whole-image results are keyed apart (decision 15, planned). The forces reach the `decompose` passes, which then rerun, as in darktable.

**Memory** (decision 15): 48 bytes a pixel of scratch, as darktable's own working set is 80 bytes a pixel with input and output: 480 MB for a 10 MP image, 2.9 GB at 61 MP, over the 2 GB budget. It stays RGBA, counted in the plan and never refused where it binds; a tiled export holds it across its rounds and sizes its tiles without it, logging the total under `-d memory` where it exceeds the budget. On lavapipe each image above 8.4 MP binds only once decision 15's image-shaped scratch in row strips is built (the decomposition's halo is 2·2ⁿ rows, at most 128), refused until then, naming the pass. Three f32 a pixel (36 bytes, 2.2 GB) waits for decision 12's packed-RGB measurement.

**Non-local means**: scratch `T`, an RGBA image of the operation's input region.

| Pass | Kind | Size | Reads | Writes |
| --- | --- | --- | --- | --- |
| `nlm_precondition` | per pixel, binding scratch, so never fused (decision 13) | the input region | the input pixel | `T` |
| `main` | spatial, radius P + R | the output | `T` within P + R; the input's alpha; the offset table | the pixel |

The structure is left to the port (decision 13): the preferred one drops `nlm_precondition` and its 16 bytes a pixel of `T`, `main` recomputing the transform from the input at each tap, which gives the same values bit for bit and is the structure the derivatives take (Gradients); the two passes stay if they measure faster at 10 MP on the M4. Either way each pixel's patch sums run in an order fixed relative to that pixel, so a tile starting anywhere gives the untiled result (Neighbourhood and scale). `main` keeps darktable's per-offset structure inside a workgroup: for each offset, the 16×16 tile's squared differences over its (16 + 2P)² footprint go into workgroup memory (each counted only when both pixels are inside the image), are box-summed along rows into a (16 + 2P) × 16 array, then each invocation sums its column of 2P + 1 and accumulates its weight and weighted pixel in registers. At P = 12, 6.4 KB and 2.5 KB of workgroup memory, under WebGPU's 16 KB; about (16 + 2P)²/256 differences per pixel per offset, against (2P + 1)² for a gather pixel by pixel. Barriers in the offset loop are reached by the whole workgroup. Its speed is to be measured (slice 8's timings, decision 15).

## Neighbourhood and scale

- **Wavelets:** whole-image passes (decision 15), at the pipe's scale in every pipe, never over a visible region; the decomposition's support grows to ±254 pixels at N = 7. darktable's own scale handling is the processing at the pipe's scale (principle 2): fewer scales below full resolution (N from s, bands keeping their frequencies), `strength × s` in the transform and `−0.5 ln s` in the bias. The manifest's radius is 0, as for the other whole-image operations. **Tiles:** one run, its only input-reading pass per pixel and writing only the pixels of its own tile, so the operation opts in (`tiles_whole_image_passes`, decision 15): every tile of an export's first round runs `precondition`, the last tile the decomposition, and the last round `main`. The 100% view and decision 15's full-resolution whole-image results come with the engine's.
- **Non-local means:** spatial, radius `P + R`, the offsets scaled by s inside `scatter` and P by `⌈radius × s⌉`, as darktable's export pipe does at any scale. At test 0027's settings `P + R = 16`; at darktable's soft limits (patch size 8, search radius 30, scattering 1) about 4,700. darktable's overlap is the same `P + K_scattered`, from the parameters. Apertrust's tiles grow by the manifests' radii, fixed, and only before demosaic, which writes exactly the tile: no operation after demosaic gets a grown input yet. Decision 13: the operation declares `Operation::reach(params, image)` = P + R at the pipe's scale, from the same setup function `prepare` uses for the offset table; export tiles are worked backward through it, demosaic writing the tile grown by the reach, once regions are worked backward after demosaic (slice 9). Where no tile size fits the grown regions, the operations up to denoise run whole, as darktable's tiling gives up; until slice 9, that fallback always applies, so non-local means' exports run untiled up to it. On lavapipe a reach above about 1,400 px is refused above 8.4 MP, an accepted exception on decision 7's list; the remedy, which comes with this port, is the offsets in groups. The kernel reads absolute coordinates, treats only the image's edges as edges (header's full size, not the region) and sums in an order fixed relative to each pixel.
- **The viewport:** both run after the downscale, at the viewport's scale, as darktable's preview pipe does, by darktable's export rule at that scale (decision 15): non-local means keeps K and scales P and the offsets, never darktable's darkroom K = max(min(4, K), K·s) or preview K = min(3, K); slice 8 times a frame at the defaults and the soft range's top, and a miss of the frame budget is decided then.

  Decision 15's full-resolution whole-image results for haze removal will run denoise at full resolution in their first round whenever haze removal is on and something upstream changes, a denoise drag included: the 100% view's round, planned in the engine before the Denoise (profiled) module ships (decision 15; `docs/engine.md`, Pipes). Until then haze removal's viewport estimates at its own scale while denoise is planned. Slices 6 and 8 time denoise at full resolution at 10 and 61 MP on the M4. If a step with haze removal on takes longer than a frame, the remedy is decided then (decision 15): the estimate held through an upstream drag, the estimate at the pipe's scale while dragging, or the cost accepted.

## Precision and special values

- **fp64 in darktable:** the `0.1 · logf(…)` of the exponent, the auto modes' `infer_*`, `scatter`'s offsets and `− 0.5 · logf(s)`: computed on the CPU in f64 as darktable's doubles, stored as f32, so nothing fp64 reaches a kernel.
- **Sums:** darktable sums each band's squares per thread in f32 (four threads, `reduction(+: sum_sq)`), Apertrust per workgroup then in one workgroup, also f32: rounding in the last bits of the thresholds, to measure.
- **The exponent:** `p ≥ 2` makes `(2 − p)` zero or negative. `p ≤ shadows ≤ 1.8` while every white balance coefficient is at least the scale s; a coefficient below `s/e²` could reach 2, which darktable divides by. The setup clamps p below 2 (1.99) so no kernel divides by zero, a departure only where darktable's output is not finite.
- **Square roots:** `√max(x² + bias', 0)` and `√A`: A > 0 from the schema's limit on the profile (`profile_a` ≥ 1e-12); the strength's minimum 0.001 keeps `k` > 0.
- **Negative and huge input:** `max(… + B, 0)` before every power, as darktable; no NaN checks (WGSL may assume none), and the output stays finite for finite input. The CPU path does not clamp the output: `− B` can leave dark pixels slightly negative, kept.
- **Determinism:** `fast_mexp2f` and `dt_fast_mexp2f` bit-exact (above); the force quantisation darktable's.

## CPU and OpenCL differences in darktable

- **Non-local means:** the OpenCL path (`USE_NEW_IMPL_CL 0`) is a different implementation, old bucket kernels accumulating each offset and its mirror, with their own edge handling; darktable's test 0027 allows 620,000 pixels between its CPU and GPU renders (`cpugpu.maxpix`), against 1,000 for 0013 and 130 for 0143. Apertrust follows the CPU's `nlmeans_core.c`.
- **Wavelets:** the OpenCL path decomposes every scale first, then synthesises coarse to fine, reading the band sums back to the host (`reduce_first`, `reduce_second`); it clamps the transform's and the inverse's results at 0 (`fmax`), which the CPU does not. Apertrust follows the CPU, its sums staying on the GPU (decision 15).
- **Compute variance:** CPU only.

## Deliberate differences

1. **darktable's compatibility paths are not ported:** `use_new_vst` off (the plain generalised Anscombe transform, `precondition` and `backtransform`) and `fix_anscombe_and_nlmeans_norm` off (the norm `0.015/(2P + 1)`, and white balance factors from `processed_maximum`, weighted 2, 1, 2 for the wavelets): darktable sets both on for every new instance and shows their toggles only while off, for edits made before darktable 2.6 and 3.0, which Apertrust does not import (decision 51). `prepare` returns `NotPorted` for either off, with a test. The migrations in `ports.rs` keep them only as far as the cases need, which have both on.
2. **Compute variance is not ported** (above): `NotPorted`, with a test.
3. **The band variances are always the whole image's** at the pipe's scale. darktable measures them per tile when it tiles the module (low memory, or a large image under its limits) and over the region its darkroom's full pipe renders at 100%, so its result there depends on its tiling; darktable-cli's export of the cases does not tile. Apertrust's tiled export equals its untiled one bit for bit (decision 13).
4. **Sums in a GPU reduction** rather than four threads' f32 sums: rounding, measured with the cases.
5. **Profiles by rawler's names and EXIF:** canonical names through rawler's own alias data and `apertrust-raw`'s renames (decisions 24 and 27), the ISO from rawler's EXIF by darktable's rule. Where they disagree with darktable's (a name the renames miss, Nikon's Lo and Hi ISOs where rawler's IFDs give no count, which is every raw but a DNG, maker-note ISOs, StandardOutputSensitivity), a camera can get another profile or the generic one, so another result; on the corpus, 34 of 40 agree, five more find none on either side, and the sixth (OM System) is fixed by the renames.
6. **No highlight preservation shift** until the decoder reads darktable's maker-note fields: `compensate_hilite_pres` is ported, its shift 0 and its default off, so a Fujifilm DR200 or DR400, a Nikon in HLG or Active D-Lighting extra high, or a Pentax with dynamic range expansion gets the profile of its recorded ISO, where darktable's default halves (or quarters) it.
7. **`p` clamped below 2** where darktable divides by zero (Precision).

None departs from what darktable-cli exports reproducibly for the cases, so no setting only the harness reaches is needed (decision 15).

## Tool binding notes

The first pass's Denoise (profiled) module mirrors darktable's page (`docs/modules/README.md`, Denoise (profiled); decisions 2 and 29), in darktable's order: Profile (the auto entry, "found ISO n", "interpolated ISO n" or "generic poissonian", then the camera's profiles by name); Compensate highlight preservation (only with a shift); Whitebalance-adaptive transform; Mode; for non-local means Patch size, Search radius, Scattering and Central pixel weight (non-local means auto hides the first three); for wavelets Colour mode and the wavelet curve, one content tab per channel (all, R, G, B in RGB; Y0, U0V0 in Y0U0V0); Adjust autoset parameters (the auto modes); Strength; Preserve shadows and Bias correction (not the auto modes). The compatibility toggles and compute variance are not shown. The module is planned.

- **Profile:** choosing a camera's profile copies its `a` and `b` and turns `profile_auto` off, as darktable's `profile_callback` copies them; the auto entry turns it on. The list needs the camera's profiles from the session (`profiles(camera)`, decision 24); copying green's `a` and `b` is all the schema stores.
- **The curve:** dragging moves `y` near the pointer with a Gaussian of the pointer's radius, `y ← (1 − f) y + f · y_mouse`, `f = exp(−(x_mouse − x_k)² / r²)` (darktable's `denoiseprofile_motion_notify`); `x` never moves.
- **Switched** (decision 32): the operation has no identity setting, so the Denoise (profiled) module is untouched while off, as darktable's is. Its controls default to darktable's (`reload_defaults`, Strength 1), any change turns it on with them, and its reset turns it off.
- **Strength 0:** darktable's minimum is 0.001, and `k = strength × cs × s` divides the transform, so the operation is undefined at 0. As strength → 0 the thresholds → 0, the weights of every non-zero offset → 0 (exactly 0 once `diss · norm − 2` exceeds 126, by `dt_fast_mexp2f`), and the bias term vanishes against `x²`, so the output tends to the input without reaching it.
- **Presets:** darktable's "wavelets: chroma only": wavelets, Y0U0V0, strength 1.2, shadows 0, bias 0, the profile automatic, every curve 0.5 but Y0's at 0, central pixel weight 0.1, adjust autoset 1, compensate highlight preservation off. `reload_defaults`'s values are the module's defaults, which it starts from once on (decision 32), so no preset holds them.

## Gradients

Decision 11: a slot only where the output pass's derivative entry points equal finite differences of whole renders.

- **Wavelets:** `bias` alone. It enters only `main`. Strength, shadows, the profile and the white balance reach `precondition` and every band's variance, and the forces the `decompose` passes, all whole-image, so their slots are undeclared.
- **Non-local means:** `strength`, `shadows`, `bias`, `central_pixel_weight`, four slots, exact by a restructure: `main`'s derivative entry points recompute the transform from the input for every tap rather than reading `T` from scratch, so the patch distances' dependence on strength and shadows is differentiated too. Patch size, search radius and scattering change integer offsets, piecewise constant: no slots.
- **Structure:** `main`'s loops are long (9 to 3,721 offsets), so, as grain's noise does, the derivative is forward mode through the loop (`fwd_diff` of the per-offset body), and the backward entry point is each slot's forward derivative dotted with dLoss/dOutput, four forward sweeps, rather than Slang's reverse mode with checkpoints written at a run-time index (decision 10). `fast_mexp2f` and `dt_fast_mexp2f` get a `[ForwardDerivative]`: the slope of their octave, `−2^(−⌊x⌋ − 1)`.
- **Non-smooth spots:** `max(·, 0)` before the powers and in the weights, the soft thresholds' kinks at ±thr, `fast_mexp2f`'s octave corners, and `√max(x² + bias' · wb', 0)`, whose derivative in the bias is unbounded where its argument nears 0 (dark pixels whose denoised value is at most 0). The bias's check may need its own step there (`ports::gradient_step`), or a GPU test at a negative bias, which the cases do not have (theirs is −0).
- Derivatives with respect to the input image are not exported (a gather's reverse mode is a scatter; `port-module`, Spatial modules).
