# 0011. A differentiable pipeline, and matching a reference photo

## Context

The third part of Apertrust's promise is that it can set the sliders for you ([0001](0001-what-apertrust-is-the-principles.md), principle 7). With gradients of the output with respect to every slider, an optimiser can move all of an edit's sliders towards a target in a few dozen small renders, and the result is ordinary module values a person can tweak. Retrofitting differentiability into kernels written without it would mean reworking them. What must every kernel provide, where is that impossible or inexact, and what proves the promise first?

## Decision

**Every differentiable operation's kernel exports `<name>_backward` and `<name>_forward_diff`**, generated by Slang ([0009](0009-slang-for-every-kernel-compiled-to-wgsl.md)), and its gradients match finite differences of whole renders within 1 % relative error on its golden case and on the synthetic sweep, with forward and reverse mode agreeing per pixel, or the gap is understood and recorded in its port spec.

**Kernels are written for it:** continuous parameters; no unnecessary hard clamps, thresholds or branches, with smooth approximations planned for the optimisation path where they are needed (clipping, hard-edged masks, medians).

**The raw stage has no derivatives.** Its parameters are never optimised, and the entry points' per-pixel RGB buffers do not fit mosaics. `Kernel::derivatives` says whether a kernel has them; the naga test requires the entry points only when it is set, and a second test holds each manifest's `differentiable` to its kernel. Matching therefore fits the light through colour calibration's `x` and `y`, after demosaic. Nor does an operation with no continuous parameter, as orientation (`flip`), input colour (`colorin`) and output colour (`colorout`): it exports no derivative entry points, its manifest not differentiable.

**A gradient slot is exact or not declared.** A slot names a parameter whose derivative from the operation's entry points equals finite differences of whole renders:

- exact as built for parameters no whole-image pass reads (the tone equalizer's bands, the bilateral grid's detail, haze removal's strength and distance);
- exact by a per-operation restructure where one exists: local laplacian's detail, shadows and highlights through pyramids of its curve's four parts, at four times the remapped pyramids' memory, built when its controls are fitted, its slots undeclared until then;
- otherwise no slot.

One exception: sigmoid's derivative with respect to its contrast, skew and targets is the smooth fit's, within ΔE2000 0.25 of the staircase its f32 fit renders, as darktable's does (`docs/ports/sigmoid.md`, Gradients).

**Through a whole-image operation, input derivatives hold its whole-image results constant**, the error against finite differences at 512 px measured and recorded per operation. Forward-mode tangents through whole-image passes (`_forward_diff` over tangent scratch, at most four directions) come only where that error spoils the fit or a fitted parameter needs them.

**The derivative dispatch:** `Pipeline::derivative` dispatches an operation's derivative entry points over the scratch its last render left, the dispatch the matching test's backward pipe uses too.

**The matching test is Phase 3's first engine work:** a command-line test that matches a reference photo by fitting the editable settings of operations after demosaic through their derivative entry points, at preview resolution (around 512 px), on real photo pairs. Its pass threshold is set with the test. The derivative interface gains input-derivative entry points with it, per-pixel operations first, and takes more than four parameters per pass; a spatial operation's input derivative records its gap as understood. In order: the input derivatives and a backward pipe, frozen; the frozen error measured; the slots audited; local laplacian's pyramids when its controls are fitted; tangents for what remains.

**What the user keeps:** the optimiser moves only the sliders the user has not set; matching has a strength; the result is ordinary module values in the history, one undo step.

## Options considered

- A forward-only pipeline with per-module auto pickers, as darktable has: each solves one narrow problem; none optimises the whole edit.
- Tangents through every whole-image pass now: every whole-image kernel differentiated, reductions and quick selects included, with up to five times the scratch.
- Reverse mode through every pass: adjoint scratch and reversed passes.
- Finite differences for every parameter feeding a whole-image result: kept as the measuring stick, too slow for fitting.
- Derivatives in every kernel, the raw stage's included: work nothing runs.

## Consequences

- Interactive editing only runs the forward pipeline; gradients cost roughly two to three renders at preview resolution.
- Later uses build on the same derivatives: batch consistency, better Auto, matching two cameras, agent-driven edits, looks learnt from the photographer's own edits.
- Open: the matching test's threshold; the frozen approximation's error per operation; whether any operation needs tangents.
