# 0085. Import in folder mode

## Context

Folder mode opens a folder as it is ([0046](0046-sidecars-are-the-truth-folder-mode-library-and-project.md)), but photos still have to get from a card or another folder onto the computer. darktable does it with copy & import (`src/libs/import.c`, `src/common/import_session.c`, `_control_import_job_run` and `_control_import_image_copy` in `src/control/jobs/control_jobs.c`): a dialog listing the source's files, its naming rules with variables, a base folder and a subfolder pattern worked out for each photo, a job that copies, and a database field that remembers what was imported. Folder mode has no database and writes nothing but sidecars, so "already imported" needs another answer. Import is a full-window sheet of [0086](0086-import-as-a-full-window-sheet.md)'s pattern and a `UserForeground` job ([0057](0057-jobs-as-darktables-control-jobs.md)). The questions are what the Import tool holds and how its destination is chosen, how photos already imported are told, what the copy guarantees, and how it is built in slices.

## Decision

**Import… in folder mode is darktable's copy & import, row for row under Apertrust's words, on the Import sheet** ([0086](0086-import-as-a-full-window-sheet.md)): the source's photos in the Browser's grid, checked to import, beside one tool, **Import**. Planned: Phase 3's step 20, in five slices, 20a1 to 20d (below): the first, 20a1, the library's side, `apertrust-cli import` and a simple sheet together, after step 19's checked copy.

- **No free text in the tool.** What a note would say is in its row's tooltip, which is also the row's accessible description: Import name's what it fills; Folder's the sample path, whether the photos go into a new folder or an existing one with its count, and that nothing there is replaced; Subfolder's which date it uses; File name's the sample name and how a taken name is continued; a disabled row's reason. - **The booleans are toggles,** as every sheet's ([0086](0086-import-as-a-full-window-sheet.md)), where darktable's import dialog has check boxes.
- **Backup** (20d), a group after Destination: a second destination, the same subfolders and names under another folder, each copy made and checked as step 19's checked copy is ([0101](0101-folders-first-libraries-optional.md)). Until 20d, the Help topic `import` shows how to back up an import with Copy to… (step 19).

- **Folder's ⌄** (20a2) **sets Folder, and changes Subfolder only where an item says so:**
  - under **New subfolders in**, the default folder (`import.default_folder`, `$(PICTURES_FOLDER)/Apertrust`, Settings › Import's Base folder), then the recent base folders (20c); picking one while Subfolder is empty also puts back One for each import, so new subfolders are made;
  - under **Into an existing folder, no subfolder**, the folder open now, where one is, and the folder last imported into, then the recent folders (20c); picking one also empties Subfolder, which its item's accessible name says;
  - then **Choose a folder…**.
- **Subfolder's ⌄** (20a1) **sets Subfolder alone,** each choice with its pattern: **One for each import** (the default pattern), **One for each day taken** (`$(EXIF.YEAR)$(EXIF.MONTH)$(EXIF.DAY)_$(IMPORT_NAME)`), **Named after the import** (`$(IMPORT_NAME)`), **None: straight into the folder**, then the recent patterns (20c).
- **The dates mixed** (20a2, with File name): while Subfolder dates its folders by the day taken and File name dates its names by today, Subfolder carries a warning button, its tooltip "Folders are dated by the day taken, names by today", its menu one item, **Date the names by the day taken too**, which puts `$(EXIF.YEAR)`, `$(EXIF.MONTH)` and `$(EXIF.DAY)` in File name for today's.
- **No Override today's date row,** a departure from darktable's rows: One for each day taken dates the folders from the photos themselves, which is what a shoot imported days later needs, and a field cleared after every import is one more row for a rare case. `import.date_override` and the CLI's `--date` stay for scripts; the sheet never shows it or sends it.
- **The menus only set the rows,** so nothing in them is out of a script's reach: a script sees `import.job_code`, `import.base_folder`, `import.subfolder` and `import.date_override`, and the CLI's flags.
- **The destination stays as it was between imports,** as darktable's settings do, an existing folder chosen for one import included, which the UX pass's usability tests watch; the footer always names it. **Default settings** (↺) puts Folder back to the default folder.
- **Two keys for the folder:** `import.base_folder` is this import's Folder, which the ⌄ and the folder button change; `import.default_folder` is the person's usual one, set in Settings › Import, so picking an existing folder for one import never loses it.
- **No folder is made until a photo is about to land in it,** made just before its first photo's temporary is written there, and a folder the import made that is left empty, by a cancel or a failure, is removed, as darktable removes an empty film roll's folder. A folder that was there before is never removed.

### Already imported: told by the destination alone

No record is kept and nothing is written on the source.

- **Where it looks:** Folder's whole tree, its pattern expanded up to its first variable that is not a fixed folder's (`$(HOME)`, `$(PICTURES_FOLDER)` and the like): `~/Pictures/Apertrust` and everything under it by default, so a card put back on another day, whose photos would go into another dated subfolder, is still recognised. Whenever Folder's tree does not already hold the default folder's (`import.default_folder`), that tree is walked too, so a card imported before under `~/Pictures/Apertrust` is still known when this import goes into an album folder elsewhere, or into one folder of that tree. The source's own folders are left out of the walk, so a source inside a tree never matches itself.
- **Also the recents** (20c): the trees of Folder's ⌄'s recent base folders and of the recent folders imported into, each walked as the default folder's is, so a card imported before into an album folder or onto a share is still known. The bar's counts' tooltip names where the check looked ("Looked in ~/Pictures/Apertrust and 3 recent folders"), from `SourceChecked`'s folders.
- **Candidates first:** a file in those trees of the source photo's main file's size and camera name, a raw's, or from 20b a photo's only image file, a JPEG alone among them: its own file name, or the camera name its `.apxmp` keeps in `xmpMM:PreservedFileName`, which every copy Import names otherwise than its source carries, one with `_01` added included. The trees are listed for names and sizes alone; a name is read from a sidecar only for a file whose size matches.
- **Then the fingerprint** ([0053](0053-finding-folders-and-photos.md)), the size and BLAKE3 over the first and last 64 KiB, read from both files, confirms each candidate; a source photo with no candidate is new without reading it. A card of 5,000 photos already imported reads about 640 MB from it, an estimate of 7 s on a UHS-I card; a new card reads nothing beyond its listing.
- **A match is a probable one:** two different photos of one name and size whose first and last 64 KiB agree would be taken for one. The mark only leaves the photo unchecked, shown, its copy named, so the person can check it; the copy never skips a photo on its fingerprint alone (below). A candidate whose fingerprint cannot be read without downloading it, a cloud file not on the disk ([0053](0053-finding-folders-and-photos.md)), leaves the photo marked as probably imported, unchecked and shown with the candidate's name, until that file is on the disk.
- **A photo of several files,** a raw and its JPEG from 20b, counts as imported once each of its files is there. One whose raw's copy is at this import's destination and whose JPEG is not counts as new for the JPEG alone, and its import copies the JPEG beside the raw's copy, under its name, never touching the raw. One whose raw is found only elsewhere in the trees counts as imported before; checking it copies the whole photo to this import's destination.
- **What it does not know:** a photo moved out of every tree the check walks, or imported under a folder outside them, counts as new. Another computer whose folders are the same share knows what this one imported.

### The copy

`LibraryCommand::Import { photos, settings }`, the photos checked, a job of kind `import` on darktable's `UserForeground` queue, cancellable, as `dt_control_import` ([0057](0057-jobs-as-darktables-control-jobs.md)).

- **One photo at a time, in the order of their paths,** as darktable's import job sorts them (`_sort_filename`), whatever the grid's sort, so `$(SEQUENCE)` numbers them in that order; from one source; a raw and a JPEG of one shot keep one name, as darktable's `dt_has_same_path_basename`.
- **Copy, never move, erase or overwrite,** step 19's checked copy ([0101](0101-folders-first-libraries-optional.md)): each file streamed into a hidden temporary in the destination folder, then renamed into place by a rename that refuses to replace a file, so a copy is whole or absent; its modified time set to the source's. Nothing is written on the source. A destination folder is made as its first photo lands, and one the import made and left empty is removed as the job ends.
- **Verify the copies** (20b, `import.verify`): each copy read back past the system's cache and compared with its source's hash before its photo counts as landed, step 19's check; a copy that differs is removed, and that photo fails alone. On by default if step 19's spike measures the read-back as cheap on a local SSD, adding at most 10% to a card import's time, the source hashed as it is copied and only the destination read back, else off.
- **A photo lands as one:** its sidecars and its JPEG first, its main file renamed into place last, its raw where it has one, else its only image file (20b), so a photo counts as landed once its main file is there. A photo whose main file did not land has the files it copied removed, as its temporary is; a name counts as taken where any of a photo's files is there, so a sidecar a crash left is never overwritten. The destination check and Try again skip each file that landed.
- **A name taken:** a sequence continues after the last file there (File name's tooltip: "Continues after 20261115_0214, already there"); under original names the copy gets `_01`, then `_02`. A photo whose file at its destination, under its name or one of its `_01` names there, is the same byte for byte, compared whole as the copy reads the source, is skipped; its sidecars, and from 20b its JPEG, missing beside that copy are copied alone under the copy's name, never over a file there. A sidecar there that differs from the source's, a diverged edit, is never written over: from 20a2, after step 12, the source's edit comes in beside the one there as two virtual copies, as [0052](0052-comparing-two-copies-of-a-sidecar.md) keeps a diverged edit; until then the photo is skipped and its sidecar not copied, Folder's tooltip counting such photos ("2 are already there with an edit of their own; their edits on EOS_DIGITAL stay there") and `Imported` naming each. From 20b a JPEG there of the copy's name that differs from the source's is left as it is ("1 has a different JPEG there; it stays as it is"), `Imported` naming it too. Any other checked photo is copied, one imported before included; the footer's count of photos copied again leaves out those that will be skipped.
- **Carried with each photo,** renamed with it: its `.apxmp` and `.apdata`, and darktable's `IMG.ARW.xmp` as it is ([0051](0051-importing-darktables-edits.md)). The source's sidecar is never written; the copy's names its new photo.
- **A copy named otherwise than its source,** by a pattern or with `_01` added, keeps its camera name in `xmpMM:PreservedFileName` in its `.apxmp`, as darktable writes it, which is what "already imported" finds it by: one sidecar for each such photo. Otherwise Import writes no sidecar unless Metadata sets something: a rating, labels, keywords and fields as values beside the edit, never steps ([0110](0110-the-metadata-tool-groups-after-exif-and-iptc-metadata-as-values-beside-the-edit.md)). The initial rating is none by default, where darktable's is 1 star.
- **Failures,** as [0056](0056-export-as-an-engine-job.md)'s for export: a photo's own failure is that photo's and the import goes on; the source or the destination failing (the card removed, the disk full, a share dropped) stops it. The copies made stay. Try again (`RetryJob`) copies what is left. Cancel leaves the copies made and no temporary.
- **Problems are shown before Import** as warning buttons on their rows, each that stops the job disabling Import with its reason: an unknown variable, a folder that cannot be made or written, a destination that is the source, lies inside it, or is anywhere on a card the source is on, not enough space. The CLI refuses a date darktable cannot read in `--date` or `import.date_override` the same way.
- **The destination opens** when the copy ends in 20a1, and from 20a2 as After import says, by default as the first photo lands: as a way in and a recent, the folder Collections opens, with no photo opened; the photo being edited has its edit saved, as every change is, and closes. Where the patterns make several subfolders, their deepest common folder is the one opened, the first subfolder chosen in Collections' tree as a click chooses it, and the others list as they are chosen, each listing its own photos as any folder does. From 20a2, after step 10, the session adds each photo copied into the folder the Browser shows to its index, so the Browser fills as they land, never reading the folder again.
- **At the end, a notice** (20a2, step 12): "Imported 214 photos into 20261115_Wedding", with **Back to 2026-10 Lisbon** where the import replaced what was open, which opens it again with its active photo. There is no Undo; copies are removed with Delete (step 19).
- **Whether the card can be formatted** (20c): the job checks the source again as it ends, the photos it copied counting as imported without a second read, and its row and the notice say **"Nothing new is left on EOS_DIGITAL"**, or "3 photos on EOS_DIGITAL were not copied", with **Eject EOS_DIGITAL** beside it. A photo any of whose files or edit stayed on the card, a JPEG or a diverged sidecar left by a clash (A name taken, above) or a file that failed, counts as not copied and is named, so "Nothing new is left" is said only when every file of every photo on the card has its copy.

### A card coming in

A card is a mounted volume with a `DCIM` folder at its top.

- **While one with photos not imported is in,** the Toolbar's Import… and Collections' ([0090](0090-export-as-a-photos-tab-tool.md)) gain a dot, each with the tooltip "EOS_DIGITAL: 214 new photos", and Import opens with it chosen. **When a card is connected** (`import.card_connected`: Do nothing, Mark Import, the default, or Open Import) lets Import open by itself. The volumes come from `apertrust-display`; counting a card's new photos is a `SystemBackground` job, never in the jobs window.
- **Eject** (20c), an action, never a setting: **Eject EOS_DIGITAL** at the job's end, beside what is left on the card (above), and on the card's row in Source's Places, the system's eject through `apertrust-display`'s platform code, disabled while a job reads the card. An automatic eject setting may come later.
- **A card opened with Open Folder…,** or any folder inside one, opens view-only, a fix ahead of Import, on its own: no rating, label, edit or sidecar is written on it, so a card browsed as a folder is never written to, not only in Import. A banner says "EOS_DIGITAL is a camera card: shown for viewing only. To work on these photos, import them." Its **Import…**, which opens the sheet with the card chosen, comes with 20a1; until then the banner has no button.

### What a script sees

- **The settings,** `import.*`: the job's own (`base_folder`, `default_folder`, `subfolder`, `file_name`, `keep_original_name`, `job_code` for Import name, `date_override`, the rating and metadata, the source's options and After import's) with owner `import`, generated by `apertrust-library`, kept by the app and read by the CLI; the sheet's own (the places, the folder, the folder last imported into, from 20c the menus' recents, and [0086](0086-import-as-a-full-window-sheet.md)'s column width, Keep open and Zoom) with owner `app`. Settings › Import shows darktable's four preference rows, Base folder (`import.default_folder`), Subfolder, File name pattern and Keep original file name (20a2), and When a card is connected (20c). The schema gains each key with the slice that first uses it.
- **The commands** (decision [0054](0054-four-layers-for-the-librarys-code.md)'s layer 4): `ListSource { source, include_subfolders }`, a cancellable `UserBackground` job of kind `import-source` with no progress, shown in the sheet alone, cancelled by the next `ListSource` or by `CancelListing { listing }`, its number, as the sheet closes, answered by `SourceListed` chunks and capture times, then `SourceChecked` against the trees above, checked again as Folder changes and, from 20c, when an import into them ends, a change cancelling the check still running, which sends nothing more, each check numbered within its listing and its `SourceChecked` naming that number and the folders it checked, the sheet keeping only the latest check's; `PreviewImport { photos, settings }`, a `UserForeground` job with no progress as Export's preview, answered by `ImportPreview` (the sample paths and folders, whether each folder is new or there already and its count, the dates each pattern uses, the clashes, the photos imported before among those checked, the size, the free space and the problems with their fixes), which the rows' tooltips and warning buttons show; `Import`, with `Imported` chunks naming each source and its copy; `Volumes`, the cards and drives mounted when the sheet opens (20a1), then as they come and go (20c). Each event carries its command's number, the sheet keeping the latest `ListSource`'s and `PreviewImport`'s, and marking photos imported only from the `Imported` of an `Import` it sent from the listing it shows, so another import's events change nothing, a card of the same name included; the folder's filter on the latest `Open` does not apply to them.
- **The CLI,** its flags named after the tool's rows: `apertrust-cli import SOURCE [--folder DIR] [--subfolder PATTERN] [--name NAME] [--dry-run]` with 20a1, only new photos, under their camera names, `--dry-run` printing the preview; with 20a2 several sources (`SOURCE...`), `--file-name PATTERN | --original-names`, `--date D` and `--all`, which imports the photos imported before too. `--folder` sets `import.base_folder`, `--name` `import.job_code`.

### Presets

The Import tool's presets (20c), from its header's presets button as every tool's, hold every setting of the tool and never the source or the checks; kept as `.appreset` files in `presets/import/` ([0106](0106-presets-and-styles-as-appreset-and-apstyle-files.md)). Default settings first; then two built in, **Original names** (Keep original file name on) and **By capture date** (Subfolder's One for each day taken and the file name `$(EXIF.YEAR)$(EXIF.MONTH)$(EXIF.DAY)_$(SEQUENCE).$(FILE_EXTENSION)`), the rest of each at darktable's defaults; then the person's own. darktable ships none. darktable's own patterns are Default settings, so no preset repeats them.

### Deliberate differences from darktable

A tool beside a grid, not a list in a dialog; thumbnails always, for the cells in sight; already imported told by the destination, not a database field, and looked for under the default folder too, its own key beside this import's Folder where darktable's preference and dialog share one; no first-time alert about the base folder, since the footer always names the destination; the checks, not a selection; a card's `DCIM` listed whole; `_01` for a taken original name and an identical photo skipped, where darktable switches to the pattern; the sidecars and darktable's `.xmp` carried; problems shown before Import, as warning buttons with their fixes; the sample path, new or existing folders and the dates used in the rows' tooltips; menus of choices on Folder and Subfolder; no Override today's date row; never an overwrite; Open the destination a choice, and Back to … after it; a card opened elsewhere view-only; no initial rating; three presets built in, where darktable ships none; the copies verified, a backup copy and Eject at the job's end, none of which darktable has; Return in Import name importing.

## Options considered

- **A record on each computer** of what was imported, in the user data folder: a second truth beside the files, unknown to another computer and lost with the user data folder, while the destination says what is really there. The recents' trees (20c) cover the folders imported into elsewhere.
- **An "Also look in" list** in Settings › Import, for an archive the photos were moved to: one more setting to keep, for a move the recents mostly cover.
- **A hidden file written on the card:** writes on the person's card (principle 3), and cameras may object to it.
- **darktable's database field,** the file name and time: folder mode has no database ([0046](0046-sidecars-are-the-truth-folder-mode-library-and-project.md)).
- **Import into a library or a project's capture folder:** no file is a library, so Import… copies into a folder in every case, and a Library adds a folder as it is ([0101](0101-folders-first-libraries-optional.md)).
- **Only the path the pattern would give:** a card put back on another day goes to another dated subfolder and looks new.
- **Only Folder's tree:** a card imported before under the default folder looks new when this import goes into an album folder elsewhere.
- **Fingerprinting every raw in the trees:** 128 KiB of every photo read on every import; the size and name narrow it first.
- **Whole files compared for the mark:** a 30 MB read of each candidate on both sides on every opening; the mark leaves the photo shown and checkable, and the copy compares whole files where it would skip.
- **Skipping a whole photo once its raw is there:** a JPEG left on the card by a raw-only import would never come.
- **The grid's sort or capture order for the copy:** two orders for one card's sequence numbers, where darktable's import job sorts by path.
- **One Folder field for the whole destination, with recents:** a departure from darktable's two settings, its preference rows, the keys and the CLI's flags; at the column's 296 to 440 points the long pattern hides the part that varies; the tree for already imported and a backup's root would come from a pattern's fixed part. Two rows let the person who imports into an album change Folder alone and the traveller Subfolder alone.
- **A New or Existing segment over the rows:** a mode of its own, a third setting over darktable's two, where Folder's ⌄ sets the same rows and empties Subfolder for an existing folder.
- **Override today's date as a row,** last and disabled while nothing uses today's date: one more row, cleared after each import, for a case One for each day taken covers. **In ⋯:** a setting that changes the names, out of sight.
- **Notes under the rows,** the sample path, the date used, new or existing and the space: free text that moves the rows below it as it changes and wraps at the column's width in Ukrainian and Polish; tooltips, the footer and warning buttons say the same.
- **One for each day taken by default:** a departure from darktable, and a wedding past midnight split in two; the ⌄ gives it in one click.
- **The destination reset at each opening:** darktable keeps it, and the footer names it on every import.
- **The folders made as the import starts:** an empty dated folder left by a cancel or a failure.
- **"Job code" or "Shoot name" as the label:** the first says nothing about what to type, the second fits a shoot but not every import; Import name is darktable's "import job" in Apertrust's words.
- **Original names and a capture-date subfolder by default:** a departure from darktable that the presets give in one click.
- **darktable's 1 star:** a sidecar beside every photo copied, and imported photos unlike opened ones.
- **Nothing when a card comes in,** or Import opening by itself by default: the first is easily missed, the second interrupts an edit.
- **A card opened with Open Folder… as any folder:** a rating or an edit written on the card, so the footer's "nothing on EOS_DIGITAL is changed" would hold only inside Import.
- **The sources in a column of their own,** as darktable's places and folders pane: three regions and a narrower grid.
- **darktable's folder clicked** for a card: a click into `100CANON` on every import.
- **darktable's switch to the pattern** for a taken original name, and copying an identical photo again: a surprise, and a duplicate.
- **darktable's `.xmp` left behind,** as its copy & import does: its ratings, labels and keywords lost to the copy.
- **Always opening the destination at the start,** as darktable: no way to import while working on another folder.
- **Non-raws from the first slice:** they need step 17's raw and JPEG groups first.
- **The whole sheet as the first slice,** after steps 10, 12 and 19: Import arrives late for live filling, the notice and the menus, none of which an import needs to work; the first slice opens the destination when the copy ends.
- **The library and the CLI before any sheet:** a photographer still has no way in from the app.
- **Verify the copies after Phase 3,** or off by default whatever it costs: the card is formatted on trust, where step 19 already builds the read-back; its default follows the measured cost.
- **Backup after Phase 3:** a travelling photographer keeps one copy until home; a second destination on step 19's copy is small.
- **Eject only as a setting,** Eject the card after each import: a card ejected by itself surprises someone about to import from it again; an action at the job's end is seen and predictable, and a setting may still come beside it. **The system's eject alone:** the end of the job is where the card's state is told.

## Consequences

- `apertrust-library` gains the import: the source's listing, the destination check, the preview and the copy, through `apertrust_base::fs`; `ops` gains the commands and events above, served by the session as jobs.
- The fingerprint is also computed for the destination check's candidates ([0053](0053-finding-folders-and-photos.md)); the jobs gain the kinds `import-source` and `import` ([0057](0057-jobs-as-darktables-control-jobs.md)).
- The settings schema gains the owner `import` with 20a1 and each `import.*` key with the slice that uses it, `import.default_folder` with 20a1 and `import.verify` with 20b, and Settings' Import page its rows with 20a2; `data/presets/import/` its two built-in files with 20c, Default settings coming from the tool's definition ([0106](0106-presets-and-styles-as-appreset-and-apstyle-files.md)).
- The app gains the Import sheet on [0086](0086-import-as-a-full-window-sheet.md)'s frame and the Import tool's declaration; the view-only rule for a card comes first, on its own; `apertrust-display` the volumes (20a1), as they come and go and Eject (20c).
- `apertrust-cli` gains `import` with 20a1, its other flags with 20a2.
- [library.md](../library.md#import-in-folder-mode) describes the library's side, [gui.md](../gui.md#the-import-sheet) the sheet, [settings.md](../settings.md) the settings and [roadmap.md](../roadmap.md#the-librarys-steps) the slices; the Help topic `import` says how to back up with Copy to… until 20d; the wireframe's Import sheet board draws it.
