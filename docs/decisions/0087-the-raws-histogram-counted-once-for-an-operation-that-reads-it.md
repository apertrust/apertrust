# 0087. The raw's histogram counted once for an operation that reads it

## Context

Exposure's automatic mode, darktable's deflicker, computes its exposure from the histogram of the raw as decoded: every photosite of the 16-bit mosaic in the image's crop, before rawprepare, in 65536 bins, at full resolution in every pipe (`docs/ports/exposure.md`). The exposure operation runs after demosaic and binds only its own input, so no operation can reach the mosaic today. darktable counts it on the CPU once per image and finds the percentile in the counts; its computed exposure also shows in the tool's panel. Every operation has a GPU path and none a CPU one ([0007](0007-a-software-gpu-instead-of-a-cpu-path.md)), nothing is read back between operations, and decision 19's readouts serve a panel, never processing ([0019](0019-scopes-and-readouts-counted-on-the-gpu.md)). How does an operation get a statistic of the raw, and how does its result reach the panel?

## Decision

**The engine counts the raw's histogram on the GPU, once per photo and only when an operation asks, reads it back once, and hands it to `prepare` in the image context.**

- **Asking:** `Operation::reads_raw_histogram(params) -> bool`, `false` by default; exposure answers true in automatic mode. `apertrust_engine::raw_histogram::read_by` resolves each instance's parameters over its defaults, as the planner does. No instance asking, nothing is counted: manual mode costs nothing.
- **Counting:** the engine's own kernel, `crates/engine/slang/raw_histogram.slang`, adds one to the bin of each photosite's 16-bit value with integer atomics straight into a counts buffer of 65536 words, which is cleared first; 256 KiB is more than workgroup memory holds. Four photosites an invocation. The mosaic is bound in row windows where it is larger than one binding ([0014](0014-row-strips-for-images-over-one-binding.md)), every window's dispatch in one submission.
- **The region:** the declared image (`Camera::declared`), the one Apertrust shows. darktable meters rawspeed's crop, which Apertrust does not know; the difference is recorded in the port's spec, and the golden comparisons meter darktable's own crop, recovered from its render, through `raw_histogram::count` with a region of the harness's ([0063](0063-departures-from-darktable-and-views-below-full-scale.md)).
- **Reading back:** the counts copied into a buffer the CPU maps and waited for: a quarter of a mebibyte, once per photo, before the first plan that needs it. This extends decision 19's readback, which never feeds processing, with one read that does: the count is the GPU's, the percentile search over 65536 counts the CPU's, as a readout's decode is.
- **Handing over:** `ImageContext::raw_histogram: Option<RawHistogram>` (`apertrust-plugin`), the counts with darktable's search (`RawHistogram::value_at`), its conversion to EV (`RawHistogram::ev`) and the exposure that puts a percentile at a target (`RawHistogram::exposure`). It is kept with the photo: the session counts it before the values report that shows its computed value, so the frame after them applies it, and before its rendered thumbnail, the one made as the photo leaves included, where the edit reads it as the frame shows it or as its file holds it; an export, the golden harness and the tools' benches before they plan, a session's export job handing the count to the engine thread as it hands its renders (`Hand::hand_commands`).
- **A failure:** the viewport renders automatic mode as manual mode and the session reports the failure once for the photo, trying again at the next values report or thumbnail, and renders the frame again once it is counted; a rendered thumbnail of an edit that reads it waits for it. An export fails, as an export fails on any GPU error, the CLI's and the golden harness's with it.
- **rawprepare's levels:** `ImageDesc::raw_black` and `raw_white`, darktable's `dsc.rawprepare`: rawprepare's four black levels averaged and rounded, and its white point, set by its output and carried to every later operation as `maximum` and `white_balance` are ([0021](0021-the-operation-interface.md)). Exposure converts the metered value with them, so an edit to Raw black/white point moves its exposure as darktable's does.
- **The panel:** `Operation::computed(id, params, image, input) -> Option<f32>`, a number the operation's setup computes for its tool, exposure's `computed_exposure`, the same function `prepare` applies. A tool shows it as a computed value (`Row::Computed`: an id, the operation, a unit and decimals), and the session reports it with the tool's state (`ToolState::computed`, `ComputedState`), computed while the row shows from a plan of the operations up to it, so on rawprepare's levels as the edit sets them. Computed values are not decision 19's readouts, counted on the GPU for a client that asks, whose names stay theirs. The design system's `ReadoutRow` draws one: the label at the start, the value at the end where a slider's ends.

## Options considered

- **The operation's own passes on the GPU:** a new `Resource::Mosaic` a post-demosaic operation binds, the count and a one-workgroup percentile scan as whole-image passes, the computed exposure read back through decision 19's readouts. Kept on the GPU throughout, but every planner, tile round and strip path after demosaic would handle a second image, the mosaic would stay resident in every pipe, and the readouts are not built.
- **On the CPU from the decoded raw:** rawler's mosaic is in host memory after decoding, about 25 ms for 48 MP on one M4 core; a CPU path over pixels, against decision 7.
- **Counted for every photo as it opens:** simpler, but every photo pays for a statistic only automatic mode reads.
- **Metering rawspeed's crop:** darktable's region exactly, through rawspeed's camera data as a data file; a parser and a file for one statistic, kept for later should exact agreement on every raw matter.

## Consequences

- `apertrust-plugin` gains `RawHistogram`, `ImageContext::raw_histogram`, `ImageDesc::raw_black` and `raw_white`, `Operation::reads_raw_histogram` and `Operation::computed`; `apertrust-tools` gains `Row::Computed` and `Computed`; the session's `ToolState` gains `computed`; `apertrust-ui` gains `ReadoutRow`.
- `docs/engine.md` describes the count beside the readouts; `docs/plugins.md` the two methods and the image context's field; decision 24's image context holds, beside the camera's data the decoder gives, the raw's histogram the engine counts.
- Cost on the M4 with the 7R V's 61 MP raw (`docs/ports/exposure.md`, Results): nothing in manual mode; in automatic mode one count per photo, 20 to 32 ms of wall time with its readback; an exposure change 7.07 ms against manual mode's 7.06; the computed value's plan 0.035 ms per values report. A Percentile or Target level drag renders as an Exposure drag does.
- Against darktable-cli in automatic mode, metering darktable's crop, 27 of the 29 corpus raws pass the exit test at 50 % and −4 EV, as in manual mode; the declared image's exposure differs from darktable's crop's by at most 0.012 EV.
- Another statistic of the raw an operation needs comes the same way, behind its own question to the operation.
